# NeSToR — локальный MVP открытой Y-STR-базы

Независимое приложение: свой код, свои SQLite-базы, CRM (`app/`) не используется
и не меняется. Работает только локально (`127.0.0.1`), облака и публичного сайта нет.

## Что есть на этапе 1

* Пользовательская база `var/nestor_users.db` (создаётся при первом запуске):
  аккаунты, профили, маркеры, журнал согласий, запросы на связь.
* Профили закрыты по умолчанию; владелец отдельно включает сопоставление.
* Подтверждение права загрузки: свой тест / тест другого человека с разрешения.
* Никнейм и дальний предок — необязательные поля с видимостью
  «скрыто / зарегистрированным / всем».
* Гостевой поиск без аккаунта: профиль не сохраняется, показываются случайные 20%
  совпадений среди открытых профилей, отсортированные по GD; повтор запроса —
  та же выборка.
* Поиск владельца по своему открытому профилю, запросы на связь без раскрытия контактов.
* Экспорт своего профиля (JSON без kit ID и email), полное удаление профиля.
* Замок научного справочника: подключается только по `data/MANIFEST.json` с SHA-256,
  только на чтение. Сейчас **не подключён** (ждёт сверки версий 45 389 / 35 284).

Решения и список ожидающего архива — в [docs/DECISIONS.md](docs/DECISIONS.md).

## Запуск на Windows

Нужен Python 3.10 или новее с python.org (тесты проверены на 3.10, 3.11, 3.13) (при установке отметить «Add python.exe to PATH»).
Сторонние пакеты не нужны.

Двойной щелчок по `nestor\run_nestor.bat`, либо в PowerShell из корня репозитория:

```bash
cd nestor
```

```bash
py -3 run_nestor.py
```

Откроется браузер на `http://127.0.0.1:8765/`. Остановить — Ctrl+C в окне консоли.

Другой порт или папка данных:

```bash
py -3 run_nestor.py --port 8800 --var-dir D:\nestor-data
```

## Тесты

```bash
cd nestor
```

```bash
py -3 -m unittest discover -s tests -v
```

(или `py -3 -m pytest tests`, если установлен pytest). Все тесты — на синтетических данных.

Покрыто: разбор и нормализация маркеров, панели (FTDNA, Genopoisk; режимы известной
панели и пользовательского набора, контрольные CSV архива) и отказ для
Y700/неподтверждённых панелей, GD, закрытость по умолчанию и журнал согласий,
отсутствие kit ID/email в результатах и экспорте, видимость полей, запросы на
связь, гостевые 20% по всему списку и сортировка по GD, повторяемость выборки,
невозможность собрать скрытый список повторами, неизменность базы при гостевом
поиске, запрет поиска закрытым профилем и закрытого профиля, удаление профиля и
аккаунта, замок справочника (SHA-256, только чтение), сквозной сценарий через HTTP
(CSRF, проверка источника запроса).

## Импорт файлов

**Пользовательские профили** (веб, «Мои профили» → «Импорт из файла CSV / XLSX»):

1. Загрузите CSV (разделитель `;`, `,` или TAB; UTF-8 или Windows-1251) или XLSX (читаются
   все листы) и выберите панель — конкретную или «определить автоматически» (только при
   надёжном совпадении по заголовкам; иначе пользовательский набор). Локусы файла вне
   выбранной панели — ошибка листа («ошибочная панель»).
2. Предварительный просмотр до записи: листы, строка заголовков, панель, число профилей,
   пропуски, нераспознанные значения, повторы внутри файла (значения / ID) и совпадения с
   уже сохранёнными профилями, исходные ячейки каждой строки.
3. Отметьте строки, укажите основание загрузки и сохраните. Профили создаются закрытыми.
   Повторы только помечаются — записи не объединяются.

**Что хранится.** До вашего решения загруженный файл лежит во временном каталоге загрузок
(Linux/macOS — `var/staging/`, права 0700; Windows — `%LOCALAPPDATA%\NeSToR\staging` в локальном
профиле пользователя с явно заданным ACL: наследование отключено, доступ только текущему
пользователю и SYSTEM; ACL проверяется при запуске, при сбое проверки загрузка файлов отключается)
(не в пользовательской базе и не в её резервных копиях). После сохранения в базе остаются только
исходные ячейки **выбранных** строк (дословно, например `33.200000000000003` — для сравнения то же
число 33.2), имя файла, лист, номера строк и SHA-256 всего файла; временные файлы загрузки
удаляются — в полном файле могут быть профили, которые вы не выбрали.

Временные загрузки удаляются без ручного вмешательства: при отмене и сохранении — сразу; новая
загрузка заменяет незавершённую; загрузки старше суток, а также остатки после сбоя процесса
(файл без метаданных, метаданные без файла, недописанные `.tmp`) удаляются при запуске
приложения, каждый час и при каждой новой загрузке.

Хранение полного оригинала для локального аудита — **отдельная необязательная отметка** на
странице проверки, по умолчанию выключена; с предупреждением, что сохранятся все строки и листы,
включая невыбранные. Такой файл хранится в пользовательской базе и удаляется из неё вместе с
последним сохранённым из него профилем и вместе с аккаунтом; в уже сделанных резервных копиях он
остаётся до их удаления по сроку (см. «Резервные копии»). Ограничения: 5 МБ, 2000 строк, одна
строка — один профиль.

**Что значит «удалено».** Данные удаляются из активной базы и из проверенных файлов приложения:
файл базы (SQLite с `secure_delete`, который перезаписывает содержимое удалённых записей в
страницах), журнал WAL (после `wal_checkpoint(TRUNCATE)` — только если checkpoint завершён; результат
проверяется, при незавершённом он повторяется при фоновой очистке) и временная папка. Приложение
**не может гарантировать** стирание с носителя: на SSD, в снимках файловой системы, в корзине, в
резервных копиях вне `var/backups/` и в любых копиях, сделанных вне приложения, данные могут
оставаться. Побайтовые тесты проверяют только файлы приложения.

**Научные кандидаты** — только оператором, в отдельную базу `var/nestor_science_candidates.db`
(не пользовательская база, не справочник, поиском не читается). Без `--commit` — только просмотр:

```bash
py -3 tools/import_scientific.py ТАБЛИЦА.xlsx --source-id ИД --title "Название" --publication "Ссылка на публикацию" --url "исходная ссылка на таблицу" --license "условия набора" --permission-status "не проверено"
```

```bash
py -3 tools/import_scientific.py ТАБЛИЦА.xlsx --source-id ИД --title "Название" --publication "Ссылка на публикацию" --url "исходная ссылка на таблицу" --license "условия набора" --permission-status "не проверено" --commit
```

Повторный импорт того же файла (SHA-256) отклоняется; записи кандидатов неизменяемы.
Файлы `.db`/`.sqlite` не принимаются: GenopoiskGD, выгрузки FTDNA и снимки научной базы
(45 389 / 35 284) этим путём не импортируются и не объединяются. Синтетические CSV архива
(`tests/fixtures/archive_examples`) — только тестовые фикстуры формата, не биологические эталоны.

## Каталог временных загрузок

Проверка при запуске выполняется автоматически; отдельно:

```bash
py -3 run_nestor.py --check-staging
```

Команда создаёт каталог, ограничивает доступ (Windows: `icacls … /inheritance:r /grant:r
*<SID пользователя>:(OI)(CI)F *S-1-5-18:(OI)(CI)F`), читает ACL обратно через Win32 API и
сообщает, кому разрешён доступ. Администраторы компьютера могут получить доступ к любому
каталогу — от них ACL не защищает. Путь можно задать переменной `NESTOR_STAGING_DIR`.

## Резервные копии

```bash
py -3 tools/backup_users.py --keep-days 14
```

Только очистка старых копий (для планировщика заданий Windows):

```bash
schtasks /create /sc daily /tn "NeSToR backup prune" /tr "py -3 C:\путь\к\nestor\tools\backup_users.py --prune-only --keep-days 14"
```

Копируется только `nestor_users.db` (через `VACUUM INTO`: согласованная копия без свободных
страниц) в `var/backups/`; временная папка `var/staging/`, серверный секрет и база научных
кандидатов в копию не входят.

Копии старше `--keep-days` (по умолчанию 14, переменная `NESTOR_BACKUP_KEEP_DAYS`) удаляются,
**когда выполняется очистка**: при запуске `backup_users.py`, при запуске приложения и каждый час,
пока оно работает, или по заданию планировщика (`--prune-only`). Это срок, применяемый при
очистке, а **не гарантированный максимум**: если не запускаются ни приложение, ни инструмент, ни
задание планировщика, старые копии остаются дольше. Данные, удалённые из активной базы (профиль,
сохранённый по согласию оригинал файла), остаются в уже сделанных копиях до их очистки. Не копируйте папку `var/` целиком другими средствами:
в неё входят временные загрузки (до суток) и секрет.

## Известные ограничения

* Node.js-архива нет: нет аудита архива. Сверка 45 389 / 35 284 сделана частично
  ([docs/SNAPSHOT_RECONCILIATION.md](docs/SNAPSHOT_RECONCILIATION.md)): это разные файлы,
  23 источника архива не проверить без него. Справочник не подключён и в поиске не участвует.
* Импорт: таблицы «строка заголовков + строки профилей» (CSV / XLSX). Форматы «маркер;
  значение» в столбик, объединённые ячейки, формулы и выгрузки со служебными блоками не
  разбираются; FTDNA-выгрузки и Strelka — только после проверки на их реальных контрольных
  файлах. Решение по научным кандидатам (перенос в справочник) не автоматизировано.
* Панели: FTDNA Y12/Y25/Y37/Y67/Y111 и Genopoisk Y37/Y50 — состав и порядок из
  `config/panels.json` проверенного архива (`data/panels_archive.json`); FTDNA Y12/Y25/Y37
  совпали с открытым описанием FTDNA. Strelka — не поддержана; Y700 — вне поддержки.
* GD — пошаговая модель с правилами T16–T18 (docs/DECISIONS.md): DYS389I + вычисленный
  DYS389B вместо DYS389II; разное число копий и разные дробные значения не входят в
  численный GD и в число сравненных локусов (по нему — порог минимума маркеров),
  показываются отдельно (дробные — с пометкой «предварительно»). Так же отдельно
  учитываются позиции без значения / с нераспознанным значением и локусы, исключённые
  пользователем; в результатах — «сравнено N из M общих позиций панелей» с причинами
  (docs/DECISIONS.md, «Учёт позиций в GD»).
* Режим панели профиля (docs/DECISIONS.md, «Панель профиля»): при выбранной или надёжно
  распознанной панели позиции профиля — её полный состав, неуказанные и пустые позиции
  хранятся как «нет значения» и попадают в `missing_or_invalid`; при неизвестной панели
  профиль — пользовательский (неполный) набор, позиции — только указанные локусы.
  Межпанельная калибровка шкал (Genopoisk ↔ FTDNA ↔ научные источники) не подтверждена
  и не применяется.
* Гость может менять запрос (например, один маркер) и получать другую случайную
  выборку; повтор **того же** запроса ничего нового не даёт. Ограничение частоты
  запросов для локального MVP не делалось — нужно перед любой публикацией.
* При 1–4 подходящих совпадениях гость видит 0 (округление вниз, чтобы не раскрывать
  единственное совпадение).
* Учётные записи локальные, без подтверждения email и восстановления пароля;
  уведомлений о запросах на связь нет — только страница «Мои профили».
* Веб-сервер — `http.server` из стандартной библиотеки: подходит для локального
  однопользовательского запуска, не для публичного сайта. Стек для дальнейшей
  разработки выбирается после аудита Node.js-архива.
* Профили FTDNA (326 тыс.) не подключены и не будут без отдельного решения.
