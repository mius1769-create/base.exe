# NeSToR — решения этапа 1 и что ждёт архив

## Границы проекта

NeSToR — независимая генеалогическая база с двумя раздельными классами данных:
научный справочник (публикации с проверяемым происхождением, отдельная SQLite только
для чтения) и пользовательские профили (добровольная загрузка, `var/nestor_users.db`).
Не подключаются и не переносятся: локальная БД Genopoisk GD, её пользовательские записи,
FTDNA-выгрузки (326 тыс.), другие локальные выгрузки Генопоиска. Научные снимки 35 284 и
45 389 не объединяются; аудит источников — [SCIENTIFIC_SOURCES_AUDIT.md](SCIENTIFIC_SOURCES_AUDIT.md).

## Статус входных материалов

Получены `Nestor_scientific_YSTR.db`, `RELEASE_VALIDATION.json`, `SHA256SUMS.txt`
(контрольные суммы сходятся) — сверка в [SNAPSHOT_RECONCILIATION.md](SNAPSHOT_RECONCILIATION.md).
Самого Node.js-архива (`Genopoisk_expert_linux_2026-10-14.tar.gz`) и контрольных файлов
импорта нет; всё, что зависит от архива, перечислено ниже как ожидающее.

## Стек

* Ядро и веб-слой — стандартная библиотека Python 3.10+ (`sqlite3`, `http.server`,
  `hmac`, `unittest`). Ноль внешних зависимостей → запуск на Windows одной командой.
* Выбор между стеком архива (Node.js) и FastAPI **отложен до аудита архива**.
  Чтобы не переписывать существующий функционал архива без необходимости:
  * логика изолирована в модулях ядра (`markers`, `gd`, `search`, `profiles`,
    `contacts`), веб-слой (`web.py`) тонкий и заменяемый;
  * алгоритм гостевой выборки зафиксирован переносимым тест-вектором
    `tests/vectors/guest_sampling_v1.json` — его можно проверить на Node.js;
  * схема SQLite — обычный SQL, читается из любого стека.
* Критерии сравнения при аудите: что в архиве уже реализовано и покрыто тестами
  (импорт, панели, GD, справочник), качество/актуальность зависимостей, удобство
  запуска на Windows, возможность переиспользовать ядро без дублирования.

## Приватность и согласие

* Профиль создаётся с `searchable = 0`. Включение/выключение — отдельное действие
  владельца, пишется в `consent_events` вместе с загрузкой и сменой видимости.
* Загрузка требует основание (`own_test` / `authorized_other`) и подтверждение права;
  сохраняется версия текста согласия.
* Наружу профиль виден только по случайному `public_handle` (`N-XXXXXXXXXXXX`),
  не связанному с kit ID. Результаты поиска сериализуются по белому списку полей:
  handle, GD, число общих маркеров, никнейм и предок с учётом видимости.
* Видимость никнейма и предка: `hidden` (по умолчанию) / `registered` / `public`.
* Связь — только запросом: владелец видит сообщение и псевдоним отправителя
  (не email), принимает или отклоняет; отправитель видит статус и ответ.
* Массовой выгрузки базы нет (она обходила бы гостевые 20%). Экспорт — только
  собственного профиля владельцем, без kit ID и email.
* Удаление профиля каскадно удаляет из активной базы маркеры, журнал согласий, запросы на
  связь и происхождение из файла. Затем выполняется `wal_checkpoint(TRUNCATE)`; его результат
  проверяется (`complete` / `incomplete` / `not_wal`) и возвращается. При `incomplete` (например,
  открыт читатель) приложение не утверждает, что WAL очищен; checkpoint повторяется фоновой
  очисткой (при запуске и каждый час).
* `PRAGMA secure_delete = ON`: SQLite перезаписывает содержимое удалённых записей в страницах
  файла базы. Это свойство файла базы, а не носителя: стирание с SSD, из снимков файловой
  системы, корзины и копий вне приложения не гарантируется. Побайтовые тесты — проверка файлов
  приложения, не доказательство стирания с носителя.
* Импорт файла: незавершённая загрузка хранится вне базы — во временном каталоге загрузок
  (`<id>.bin` + `<id>.json`, атомарная запись), поэтому не попадает в резервные копии базы.
  Защита каталога (`nestor_app/secure_dir.py`): Linux/macOS — 0700 и владелец — текущий
  пользователь (файлы 0600); Windows — chmod не задаёт ACL, поэтому каталог по умолчанию в
  `%LOCALAPPDATA%\NeSToR\staging`, ACL задаётся явно через icacls по SID (наследование
  отключено, доступ только текущему пользователю и SYSTEM) и читается обратно через Win32 API;
  любой разрешающий ACE для другого субъекта, NULL DACL или включённое наследование — провал
  проверки, и загрузка файлов отключается. Администраторы компьютера ACL обходят. Срок — 24 часа; удаление без ручного вмешательства: отмена и сохранение — сразу, новая
  загрузка заменяет незавершённую, фоновая очистка (запуск, каждый час, каждая загрузка) удаляет
  просроченные загрузки и остатки после сбоя процесса.
* После сохранения в базе остаются ячейки выбранных строк, имя файла, лист, номера строк и
  SHA-256 файла. Полный оригинал — только по отдельному необязательному согласию
  (`import_files.keep_original`, время согласия), по умолчанию выключено, с предупреждением о
  невыбранных строках и листах; удаляется из активной базы с последним профилем из файла и с
  аккаунтом.
* Резервные копии (`tools/backup_users.py`): только пользовательская база, через `VACUUM INTO`,
  в `var/backups/`. Срок `--keep-days` (по умолчанию 14) применяется, когда выполняется очистка:
  запуск инструмента, запуск приложения и ежечасно при его работе, задание планировщика
  (`--prune-only`). Это не гарантированный максимум: если очистка не запускается, копии остаются
  дольше. Удалённые из активной базы данные (в т.ч. сохранённый по согласию оригинал) остаются
  в уже сделанных копиях до их очистки; копии вне `var/backups/` приложение не видит и не удаляет.
* Обновление схемы: v5 удаляет полные файлы, сохранённые прежней версией без согласия;
  v6 удаляет из базы незавершённые загрузки, хранившиеся там прежней версией.
* Владелец ищет только своим **открытым** профилем (взаимность): закрытый профиль
  не участвует в поиске ни с какой стороны.

## Гостевой поиск

* Профиль гостя не сохраняется (тест проверяет, что база не меняется), тела
  запросов не логируются.
* Подходящие совпадения: GD ≤ порога и общих маркеров ≥ минимума, только среди
  открытых профилей.
* Выборка: `k = floor(n × 0.2)` из **всего** списка подходящих; ключ
  `HMAC-SHA256(серверный секрет, канонический запрос)`, вес совпадения
  `HMAC-SHA256(ключ, handle)`, берутся k с наименьшим весом, затем сортировка по GD.
  Тот же запрос (в т.ч. с другим порядком маркеров) → та же выборка.
* `floor`, а не `ceil`: при 1–4 совпадениях гость не видит ничего, иначе
  единственное совпадение раскрывалось бы целиком.

## Правила GD (решения заказчика, 2026-11-03)

Реализовано в `nestor_app/gd.py`, описано в `data/transform_rules.json`:

* **T16 DYS389** — исходные DYS389I/II не меняются; в GD входят DYS389I и вычисленный
  DYS389B = II − I (помечается в `derived_loci`); DYS389II в GD не входит.
* **T17 копии** — разное число копий не даёт +1: локус не входит ни в численный GD,
  ни в счётчик `compared`; показывается только в `copy_count_differences`;
  порядок копий не фиксирован; DYS385 — пара; DYF404S1, DYS527 — 1 или несколько значений.
* **T18 дроби** — без округления; точное совпадение — 0; разные дробные значения не
  переводятся в шаги: `allele_differences`, `preliminary = True`, в `compared` не входят.
* **Учёт позиций в GD.** Позиции профиля без значения (`МАРКЕР=`, 0, NA …) и с
  нераспознанным значением сохраняются в профиле (`profile_markers.status`:
  `ok` / `missing` / `invalid`, исходная строка хранится). Каждая общая позиция панелей
  попадает ровно в одну категорию, проверка идёт в этом порядке:

  | Порядок | Категория | Что значит | В GD | В `compared` |
  |---|---|---|---|---|
  | 1 | `user_excluded` | локус исключён настройкой пользователя (DYS389II → DYS389B) | нет | нет |
  | 2 | `missing_or_invalid` | у одного или обоих профилей нет значения или оно не распознано | нет | нет |
  | 3 | `copy_count_differences` | корректные вызовы у обоих, разное число копий (T17) | нет | нет |
  | 4 | `allele_differences` | дробное различие без перевода в шаги (T18), GD «предварительно» | нет | нет |
  | 5 | `compared` | значения сравнены и вошли в численный GD | да | да |

  `panel_overlap` — общие позиции панелей двух профилей после приведения алиасов к
  каноническим локусам и правила DYS389 (T16); `panel_overlap` = сумма пяти категорий.
  Порог минимума маркеров (`min_common`) проверяется только по `compared`.
  Исключённые локусы входят в ключ гостевой выборки (без исключений ключ прежний, guest-v1).

## Панель профиля

* **Известная панель** — выбрана пользователем или надёжно распознана. Позиции профиля
  = полный состав панели в её порядке; неуказанные и пустые позиции сохраняются как
  «нет значения» (`profile_markers.status = missing`) и в GD попадают в
  `missing_or_invalid`. Локус вне выбранной панели — ошибка (значения не переносятся
  молча). В профиле хранится `panel_code` и `panel_basis` (`selected` / `recognized`).
* **Надёжное распознавание** (`panels.recognize_panel`): все указанные локусы входят в
  панель и покрывают не меньше 90% её позиций; из подходящих берётся наименьшая;
  при равных по размеру кандидатах распознавание не выполняется.
* **Пользовательский набор** (`panel_basis = custom`) — панель неизвестна: позиции
  = только указанные локусы; в интерфейсе — «пользовательский набор (неполный)».
* Порог `min_common` в обоих режимах считается только по `compared`.
* Составы панелей: `data/panels_archive.json` (из `config/panels.json` архива,
  SHA-256 `822f890e…`); контрольные файлы разбора — синтетические CSV архива в
  `tests/fixtures/archive_examples` (README архива: «synthetic parser controls»).

## Импорт файлов

* Два пути: профили владельца (веб, `user_import`) и научные кандидаты (CLI оператора,
  `candidates`, отдельная база). Кандидаты не читаются поиском и не входят в справочник
  до отдельного решения по источнику; поле `decision` фиксирует это.
* Перед записью — предварительный просмотр; без подтверждения ничего не создаётся.
* Сохраняются SHA-256 исходного файла, лист, номер строки и исходные ячейки выбранных строк
  дословно (полный файл — только по отдельному согласию, см. «Приватность и согласие»);
  преобразования (панель, пропуски, нормализация чисел) — отдельно, в позициях профиля.
* Повторы значений / ID внутри файла и совпадения с сохранёнными записями только
  помечаются; объединения нет. Повторный импорт файла кандидатов по SHA-256 отклоняется.
* `.db` / `.sqlite` не принимаются (GenopoiskGD, FTDNA-выгрузки, снимки научной базы).
