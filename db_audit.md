# GENOPOISK CRM — аудит схемы БД

Состояние на ветке `claude/haplogroup-color-logic-o5yk0q` (Release 1.1,
до push). Для каждой запрошенной таблицы: поле, тип, назначение,
используется ли в UI, используется ли в коде. Использование проверено
прямым поиском по `app/*.py` (не по памяти/предположению) — там, где
найден реальный «мусор», это явно отмечено в разделе «Находки» под
таблицей.

Помимо девяти запрошенных таблиц в БД есть ещё: `schema_version`,
`product_mappings`, `operators`, `delivery_methods`, `gnpsk_counter`,
`legacy_excluded_tests`, `settings`, `import_errors` — все активно
используются (справочники, счётчик номеров GNPSK, журнал ошибок
импорта), в этот аудит не включены, т.к. не запрашивались явно.

## test_types

| Поле | Тип | Назначение | В UI | В коде |
|---|---|---|---|---|
| code | TEXT PK | Код типа теста (Y50, MTDNA…) | да (везде) | да |
| display_name | TEXT | Отображаемое имя | частично — **фактическое имя в UI берётся из `product_catalog.py` (статический справочник), а не отсюда** | да, но дублирует `product_catalog.CATALOG[].display_name` |
| base_deadline_days | INTEGER | Норматив срока | нет напрямую | да, основа расчёта дедлайна |
| report_allowed | INTEGER (0/1) | Разрешён ли доп. отчёт | да (форма заказа блокирует опцию) | да |
| report_extra_days | INTEGER | Доп. дней при отчёте | нет напрямую | да |
| is_active | INTEGER (0/1) | Активен ли тип теста | нет фильтра в UI напрямую | да (`list_test_types(active_only=True)`, используется в 3 диалогах) |
| sort_order | INTEGER | Порядок сортировки | да (порядок в формах/справочниках) | да |
| price | REAL | Цена продажи (Дашборд v2) | да («Настроить цены», таблица «Экономика») | да |
| cost_price | REAL | Себестоимость (Дашборд v2) | да | да |

**Находки:** `display_name` здесь и `display_name` в
`product_catalog.CATALOG` — **два разных источника одного и того же
имени теста**. Сам `product_catalog.py` прямо документирует себя как
«единственный источник правды для отображаемых названий» и что
«ничего, кроме этого файла, не должно хардкодить пользовательские
названия» — то есть `test_types.display_name` архитектурно избыточен,
UI его не читает вообще (везде используется
`product_catalog.get_display_name(code)`). Это не баг (значения сейчас
совпадают), но потенциальный источник рассинхронизации, если кто-то
поправит одно и забудет другое. Стоит решить на этапе аудита: либо явно
пометить `test_types.display_name` как unused/legacy, либо убрать из
схемы при следующей чистке.

## report_services

| Поле | Тип | Назначение | В UI | В коде |
|---|---|---|---|---|
| id | INTEGER PK | Идентификатор | нет | да |
| order_id | INTEGER FK→orders | Заказ, к которому добавлен отчёт | нет | да (INSERT) |
| test_id | INTEGER FK→tests, NULL | Конкретный тест или весь заказ | нет | да (INSERT) |
| added_at | TEXT (ISO) | Дата добавления услуги | нет | да (INSERT) |
| notes | TEXT | Примечание | нет | никогда не заполняется |

**Находки — это самая заметная «дыра» аудита.** Таблица только
**записывается** (`create_order_with_tests()` вставляет строку, если
`report_added=True`) и **никогда не читается** — ни одного `SELECT FROM
report_services` во всём коде. Нет UI, который бы показывал, у каких
заказов есть услуга «Отчёт», нет счётчика, нет экспорта. Раз вы
планируете отдельную подсистему «Отчёты» следующим большим блоком — это
прямая точка пересечения: либо `report_services` станет основой очереди
отчётов (тогда её стоит развить: статус, дедлайн, аналитик — во многом
то же самое, что уже зарезервировано в `haplogroups.RESERVED_FIELDS`),
либо новый модуль будет жить отдельно, и тогда `report_services`
сейчас — мёртвый груз, который стоит либо начать использовать, либо
явно решить, что он войдёт в будущую схему отчётов как есть.

## Сводка находок (что реально требует решения)

1. **`report_services`** — пишется, никогда не читается. Самая явная
   находка аудита. Прямо пересекается с будущим модулем «Отчёты».
2. **`haplogroups.RESERVED_FIELDS`** (5 полей) — осознанный задел под
   отчёты, уже поддержан на уровне репозитория, не подключён к UI.
3. **`test_types.display_name`** — дублирует источник правды
   (`product_catalog.py`), в UI не используется, риск рассинхронизации.
4. **`orders.source`** — пишется («manual»/«Telegram»), нигде не
   читается/не фильтруется/не экспортируется.
5. **`test_events.internal_note`** — колонка и API готовы, но никакой UI
   не даёт её заполнить.

Ничего из этого не ломает текущую работу приложения — это дефициты
использования, а не структурные баги. Пункты 1 и 2 стоит учитывать
явно при проектировании модуля «Отчёты», а не чистить сейчас как мусор.
